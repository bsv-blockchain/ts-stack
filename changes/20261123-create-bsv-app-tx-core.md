Generated projects now use @bsv/sdk ^4.0.1 and @bsv/auth ^0.1.8. Add mode raises an existing project's outdated dependency floors and reports what it changed or could not change: a same-major raise applies to any package (for example qrcode ^1.4.0 to ^1.5.0), a cross-major raise (for a 0.x range, across a minor version) of an @bsv package create-bsv-app pins is asked for in the interactive terminal and otherwise left with a warning naming the package, the range found and the range the generated code needs, unless --upgrade-bsv-deps is passed, and any other package that would need a major upgrade, such as express ^4 where wallet-login needs ^5, is left and reported to check manually. New pre-selected tx-core capability: @bsv/wallet-helper ^0.2.0 TransactionBuilder and getAddress from @bsv/wallet-helper documented with examples, plus dataScript and internalizePayment, transaction and BEEF parsing helpers, and a Transactions demo page at /transactions. Add mode now also adds the capabilities a selected one requires where the layout uses them (for example wallet-connect for tx-core, only when the project has a frontend, since only the tx-core demo page uses it; a backend-only project gets tx-core without the relay files, dependencies or wiring), records them in bsv-scaffold.json and says so in the terminal prompt, the --ui page and the run summary. Add mode with --file keeps the capabilities the project's manifest already records. A capability that cannot be placed in the project's layout is rejected with a config error instead of being recorded with nothing written. Capability lists are resolved and recorded in registry order. Generated AGENTS.md follows the project layout: frontend-only and backend-only projects no longer get wiring snippets, file descriptions or install lists for a side they do not have, and manual wiring names each base file under its target (for example src/index.ts in a backend-only project). New projects with an explicit non-root target folder for a single-target layout now scaffold the framework into that folder; it was scaffolded at the root while capability files went to the folder.

## Migration

No consumer migration is required. Existing projects keep their dependency ranges until the next add-mode run, which merges the manifest's capabilities (tx-core included) and raises outdated ranges. devDependencies and unrecognised ranges are never changed and are listed for manual review. An add-mode run that selects a capability without what it requires now also writes the required capability's files and dependencies and records it; existing files are still skipped unless --force is given. Add-mode --file configs no longer drop the manifest's recorded capabilities, so they need not repeat them; keys such a config leaves out (network, bsvDir, stack, targets, name) now come from the manifest instead of resetting to defaults. A project with no detectable frontend or backend must declare its stack (for example --frontend react, or a stack in the --file config) before capabilities can be added.
