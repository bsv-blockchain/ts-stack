# R1C (`R1Comb`) vectors

`R1Comb` must build the same bytes as the BSV Wallet Vault, which spends with
`packages/expo-wallet-toolbox/core/services/vault/r1comb.ts` in
[bsv-blockchain/bsv-wallet](https://github.com/bsv-blockchain/bsv-wallet).
That module uses `@noble/curves`; `R1Comb` uses `@bsv/sdk` `Secp256r1`. The
script bytes are a consensus contract, so these files hold the two equal.

- `vectors.json` was generated by the Vault module (toolbox 0.26.0 candidate)
  from deterministic keys and salts: key encodings and refusals, comb-table
  and commitment hashes, locks for N = 1..5, version-1 spends with their
  preimages, digests, `fullR`, OP_PUSH_TX values and full unlocks (from
  low-S and high-S DER), plus `recode` and script-number cases.
- `51c53430…579a_0.hex` is an R1C-geometry lock mined on testnet, and
  `476611a4…4b80.hex` is the transaction that spent it. Both are copied from
  that repository's `docs/example-txs/`.

`src/__tests/R1Comb.test.ts` checks every value. The toolbox's own
`__tests__/vault/r1comb.test.ts` (189 tests) also passes with `R1Comb` in place
of its module.

To regenerate `vectors.json`, copy `generator.toolbox.ts.txt` to
`packages/expo-wallet-toolbox/__tests__/gen/r1vectors.test.ts` in bsv-wallet
and run it with `R1_OUT=<path> pnpm exec jest <that file>`. Always generate
from the Vault module, never from `R1Comb`: vectors from the code under test
prove nothing.
