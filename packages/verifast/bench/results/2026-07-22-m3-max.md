# VeriFast serialization and batch benchmark — 2026-07-22

This retained run validates the real BDK WASM artifact after adding typed and
memoized EF serialization, pre-serialized verification, Spend verification,
packed batches, explicit networks, and separate Node/browser/UMD loaders.

## Environment

- MacBook Pro, Apple M3 Max, 128 GB RAM
- macOS 26.5.1 (25F80), arm64
- Node v25.9.0, pnpm 10.33.2
- `bdk-core.wasm` SHA-256:
  `e3902a58e5db58e59d391bd69ce163c7aee6acc92dc7b9bc1559667761de7c60`
- WASM size: 3,013,717 bytes
- Node, browser, and UMD WASM outputs had identical SHA-256 digests

## End-to-end transaction verification

Command: `pnpm --filter @bsv/verifast bench`

Each sample contains 100 complete `Transaction.verify('scripts only')` calls;
the table reports the median of seven alternating samples.

| Vector | Inputs | JS median | BDK median | JS inputs/s | BDK inputs/s | Speedup |
|---|---:|---:|---:|---:|---:|---:|
| P2PKH | 1 | 115.7 ms | 6.6 ms | 864 | 15,265 | 17.66x |
| P2PKH | 5 | 557.0 ms | 27.8 ms | 898 | 18,003 | 20.06x |
| P2PKH | 20 | 2,202.1 ms | 111.2 ms | 908 | 17,981 | 19.80x |
| OP_TRUE | 1 | 0.1 ms | 0.3 ms | 986,028 | 305,033 | 0.31x |
| Arithmetic | 1 | 0.3 ms | 0.4 ms | 314,713 | 262,669 | 0.83x |
| SHA-256 preimage | 1 | 0.4 ms | 0.3 ms | 257,317 | 304,568 | 1.18x |

The SDK orchestration-only diagnostic lane sustained 2,628,674 inputs/s, while
the direct one-input BDK lane sustained 18,275 inputs/s. Signature verification,
not SDK dispatch, remains the dominant P2PKH cost.

The built browser package was also executed in headless Chrome through the
conditional browser export. Across 50 iterations and five samples, the P2PKH
speedups were 13.14x, 14.92x, and 14.63x for 1, 5, and 20 inputs respectively.

## Packed batch ABI

Command: `pnpm --filter @bsv/verifast bench:batch`

Each row is the median of seven complete batches using the same valid one-input
P2PKH transaction. “Singles” performs one JS/WASM call per item; “packed” uses
one call and contiguous typed buffers.

| Items | Spend singles | Spend packed | Spend gain | EF singles | EF packed | EF gain |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 0.136 ms | 0.145 ms | 0.94x | 0.090 ms | 0.102 ms | 0.89x |
| 10 | 0.732 ms | 0.650 ms | 1.13x | 0.583 ms | 0.523 ms | 1.11x |
| 50 | 3.201 ms | 2.904 ms | 1.10x | 2.879 ms | 2.494 ms | 1.15x |
| 250 | 13.582 ms | 13.327 ms | 1.02x | 12.622 ms | 12.242 ms | 1.03x |

Packing removes measurable boundary overhead at moderate batch sizes. At 250
P2PKH inputs the fixed overhead is amortized and ECDSA dominates, so claiming a
large cryptographic speedup from batching would be misleading. The API's main
capacity benefit is a bounded buffer and one host/WASM transition per chunk.

A 250-Spend packed call retained no measurable heap or RSS after forced garbage
collection on this run (heap delta -0.13 MiB, RSS delta 0.00 MiB).

## EF serialization

The fixture has one signed P2PKH input and an unexecuted output script of the
listed size. “`number[]` cold” calls the compatibility `toEF()` API after a
mutation; “typed cold” calls `toEFBinary()` after a mutation; “cached typed”
reuses `toEFBinary()` without mutation.

| Script | EF bytes | `number[]` cold | Typed cold | Cached typed | Cold gain |
|---:|---:|---:|---:|---:|---:|
| 1 KiB | 1,233 | 0.021 ms | 0.010 ms | 0.0002 ms | 2.00x |
| 64 KiB | 65,746 | 1.067 ms | 0.019 ms | <0.0001 ms | 55.01x |
| 1 MiB | 1,048,786 | 16.650 ms | 0.196 ms | <0.0001 ms | 85.15x |
| 4 MiB | 4,194,514 | 67.695 ms | 0.821 ms | <0.0001 ms | 82.46x |

These figures isolate serialization and legacy array conversion, not complete
script verification. The practical verifier win depends on how much ECDSA or
script execution follows. Callers that already hold EF should use
`verifyScriptsFromEF`; repeated `Transaction` verification benefits from the
mutation-aware cache automatically.
