# VeriFast serialization and batch benchmark — 2026-07-22

This retained run validates the real BDK WASM artifact after adding typed and
memoized EF serialization, pre-serialized verification, Spend verification,
packed batches, explicit networks, and separate Node/browser/UMD loaders.

## Adaptive routing validation

The default integration mode now selects WASM only after it is ready and at
least one source locking script either exceeds 100 bytes or contains
`CHECKSIG`, `CHECKSIGVERIFY`, `CHECKMULTISIG`, or `CHECKMULTISIGVERIFY`.
Selection is opcode-aware: signature-opcode byte values inside pushed data do
not qualify a script.

The retained unit and clean-package consumer runs prove these boundaries:

- an eligible cold transaction and Spend complete through the existing SDK
  interpreter before the deferred WASM factory is invoked;
- after `preload()`, the same P2PKH transaction and Spend select WASM;
- exactly 100 non-cryptographic bytes stay on JavaScript, while 101 bytes select
  WASM;
- a selected backend remains authoritative and failures are never retried on
  JavaScript;
- Node ESM, Node CommonJS, browser ESM, and browser UMD consumers exercise the
  readiness API; the SDK-backed consumers also prove warm P2PKH selection.

## Packed batch ABI

Command: `pnpm --filter @bsv/verifast bench:batch`

Each row is the median of seven complete batches using the same valid one-input
P2PKH transaction. “Singles” performs one JS/WASM call per item; “packed” uses
one call and contiguous typed buffers.

| Items | Spend singles | Spend packed | Spend gain | EF singles | EF packed | EF gain |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 0.146 ms | 0.135 ms | 1.08x | 0.089 ms | 0.103 ms | 0.87x |
| 10 | 0.745 ms | 0.645 ms | 1.16x | 0.633 ms | 0.562 ms | 1.13x |
| 50 | 3.156 ms | 2.821 ms | 1.12x | 2.931 ms | 2.738 ms | 1.07x |
| 250 | 14.402 ms | 13.822 ms | 1.04x | 13.589 ms | 13.248 ms | 1.03x |

Packing removes measurable boundary overhead at moderate batch sizes. At 250
P2PKH inputs the fixed overhead is amortized and ECDSA dominates, so claiming a
large cryptographic speedup from batching would be misleading. The API's main
capacity benefit is a bounded buffer and one host/WASM transition per chunk.

A 250-Spend packed call retained no measurable heap or RSS after forced garbage
collection on this run (heap delta -0.01 MiB, RSS delta 0.00 MiB).

## EF serialization

The fixture has one signed P2PKH input and an unexecuted output script of the
listed size. “`number[]` cold” calls the compatibility `toEF()` API after a
mutation; “typed cold” calls `toEFBinary()` after a mutation; “cached typed”
reuses `toEFBinary()` without mutation.

| Script | EF bytes | `number[]` cold | Typed cold | Cached typed | Cold gain |
|---:|---:|---:|---:|---:|---:|
| 1 KiB | 1,233 | 0.021 ms | 0.003 ms | 0.0001 ms | 6.22x |
| 64 KiB | 65,746 | 1.005 ms | 0.013 ms | <0.0001 ms | 75.76x |
| 1 MiB | 1,048,786 | 17.025 ms | 0.128 ms | <0.0001 ms | 132.76x |
| 4 MiB | 4,194,514 | 67.069 ms | 0.382 ms | <0.0001 ms | 175.61x |

These figures isolate serialization and legacy array conversion, not complete
script verification. The practical verifier win depends on how much ECDSA or
script execution follows. Callers that already hold EF should use
`verifyScriptsFromEF`; repeated `Transaction` verification benefits from the
mutation-aware cache automatically.
