# VeriFast benchmark — 2026-07-15

This is an end-to-end comparison of `Transaction.verify('scripts only')` using
the SDK `Spend` interpreter and the bundled BDK WASM verifier. Timings include EF
serialization, the WASM boundary, BDK parsing, and transaction bookkeeping.
Module initialization and one JIT warmup call were excluded.

## Environment

- MacBook Pro, Apple M3 Max, 128 GB RAM
- macOS 26.5.1 (25F80), arm64
- Node v25.9.0, pnpm 10.33.2
- Google Chrome 150.0.7871.116, headless
- `bdk-core.mjs` SHA-256: `43d89e1fe7eb9dee1003d3914acd459538f7877432510f823594eb61a52e131e`
- `bdk-core.wasm` SHA-256: `7d16d1d4e2efe1adab1d78685f31cb40ca08bacb2f24b432e60a26a9ed49d110`

## Curve and boundary controls

All direct measurements use the real mainnet P2PKH vector. The final bulk-array
ABI reaches 51.97 us/verification (19,242/s). The legacy pre-created-vector ABI
isolates curve and interpreter execution at 50.74 us (19,709/s). Matching native
BDK is 23.44 us (42,661/s), so the final WASM verifier is about 2.2x from native
machine code on this arm64 host.

Representative retained compiler experiments show where the speedup came from:

| Curve configuration                                  | Direct WASM us/op | Outcome  |
| ---------------------------------------------------- | ----------------: | -------- |
| Default `__int128` lowering                          |             113.6 | Baseline |
| `int128_struct`                                      |              84.5 | Rejected |
| wasm32 `int64` limbs                                 |              51.7 | Adopted  |
| `int64`, ecmult window 10                            |              54.8 | Rejected |
| `int64`, ecmult window 12                            |              53.2 | Rejected |
| `int64`, ecmult window 15, Binaryen `-O4 --converge` |              50.7 | Final    |

The standalone ECDSA verifier accounts for nearly all of the final interpreter
time: the bundled BSV libsecp256k1 0.5.1 curve benchmark averaged 47.9 us versus
50.7 us for complete `VerifyScript`. Bitcoin Core libsecp256k1 0.7.1, built with
the same Emscripten, `int64`, and window-15 settings, also averaged 47.9 us;
current upstream HEAD `ebf5943` averaged 48.9 us. Neither newer curve revision
offered a measured speedup, so neither was substituted into the consensus-derived
BSV build.

For this scalar dependency-heavy workload, `-msimd128`, LTO, native WASM
exceptions, `emmalloc`, `mimalloc`, and overriding libsecp256k1 from its chosen
`-O2` to `-O3` did not improve throughput and were not retained.

## Interpretation

The BDK backend is decisively faster for signature-heavy transactions: 16-20x
in Node and 12-14x in Chrome end to end. Native secp256k1 on this Apple Silicon
host uses optimized portable C because the pinned BSV library has no arm64
assembly backend; WASM remains about 2.2x slower than that native control.

Pure SDK remains faster for trivial scripts because EF serialization, the WASM
boundary, and BDK parsing dominate when there is no elliptic-curve work. The
original parity result in this file was invalid: a root dependency override had
resolved VeriFast's development SDK to registry version 2.1.3, whose
`Transaction.verify` did not accept the verifier argument. The workspace-scoped
override now binds VeriFast to the local SDK, and the diagnostic lanes separately
measure direct BDK adapter time and SDK orchestration overhead to prevent the same
false comparison from recurring.
