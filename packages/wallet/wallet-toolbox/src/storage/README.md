# WalletStorage

Provides access to persistent storage in support of Wallet.interfaces.

This includes:

- Direct storage on a variety of databases.
- Remoted storage to service providers for backup and mobile support.
- Synchronization between multiple stores.
- Import from legacy stores.
- Support single user, multi-read/single write, full multi-user modes.

## Failed Transaction Output Handling

When a transaction is marked `failed`, storage must repair both sides of the optimistic
UTXO state created while the action was being built:

- Inputs selected by that transaction are released by clearing `spentBy` and setting
  `spendable` back to `true`.
- Outputs generated by that same failed transaction are made inert by clearing `spentBy`
  and setting `spendable` to `false`.

This distinction matters because created output rows can exist before a transaction is
signed, broadcast, or proven. If a later construction, review, or delayed-send step fails,
those rows must remain as history only; they must not be treated as funding candidates or
left as phantom UTXOs in raw storage accounting. `reviewStatus` repeats the same repair for
legacy rows and only restores inputs or neutralizes generated outputs when the failed
transaction has no active ProvenTxReq that could still reconcile.

## Invalid-change review

Invalid-change review never treats provider absence, timeout, or failure as
spent evidence. It classifies candidates as confirmed unspent, confirmed spent,
or unknown with bounded concurrency. Read-only review returns conclusive spent
rows without throwing on unknown. Direct destructive release remains atomic:
any unknown throws `WERR_UTXO_REVIEW_INCONCLUSIVE` before output state changes.
The authenticated Monitor Admin path is explicitly different: it reviews 20
rows per request and can release only the positively spent subset while
retaining and reporting unknowns, allowing a heavy wallet to make progress
without one permanently unavailable outpoint blocking all cleanup. Every row
is re-read under the write lock; an ownership, spendability, or allocation race
aborts that page. `InvalidChangeRelease`, `InvalidChangeConclusiveRelease`, and
`InvalidChangeReleaseBlocked` events retain bounded counts, values, and provider
evidence.

## Resumable ownership admission (unpublished #544 candidate)

The manager bounds `withAccess` requests to 1,032 even while availability I/O
precedes queue selection, with at most 1,024 queued operations and eight concurrent reads
for a provider that explicitly supports them. Foreground operations can pass a
background page at most eight grants or one second of queue age. Saturation
rejects the new request without replacing admitted work or choosing a legacy
fallback. The waiter bound is a count limit, not a claim about arbitrary caller
payload allocation.

Paged sync removes a cancelled waiter before writer admission. Once the
operation starts, cancellation waits for its durable acknowledgement and actual
cleanup. Durable journal status observation stays available after cancellation
so a lost reply cannot erase committed progress. Selection and current manager
generation are checked again under actual ownership.

Ownership callbacks use the supplied provider. They must not recursively acquire
the same manager queue. `runAsSync(callback, activeSync)` is the explicit legacy
borrowed-provider path for an already held exclusive operation; it grants no
new ownership. Paged progress callbacks run outside page ownership.

The [implementation map](../../docs/implementation-544.md) distinguishes authored
components from required qualification. No source-only case or documentation
entry establishes production readiness.
